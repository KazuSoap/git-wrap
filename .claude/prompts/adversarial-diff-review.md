# 変更差分に対する敵対的検証（収束型レビュー）

## 位置づけ

マージ・ブランチ・コミット範囲などの**変更差分**を、指摘 → 指摘自体の妥当性検証 → 再修正のループで**収束するまで**回すための作業手順。下のプロンプトをそのまま貼り、`<>` の箇所だけ埋めて使う。

- **スキルではない**（`.claude/skills/` の外に置いてある）。自動では起動しない。起動する／しないの判断は人が行う。
- **ファイルを変更しない読み取り専用の手順。** 修正の適用は別作業。ここでの成果物は「収束した指摘一覧」だけ。
- `doc-consistency-check`（doc↔ソースの機械照合）とは別物。あちらは**整合の網羅チェック**、こちらは**変更の妥当性と副作用の追及**。両方を通すのが望ましい。
- 想定所要は差分3ファイル程度で 15〜25 分（実測: 反復3回・probe 2本・pytest 1回）。

---

## プロンプト本文

```
<検証対象>に対して敵対的検証を実行して。

## 検証対象

<以下のいずれかで指定>
- マージコミット: <hash> [, <hash> ...]
- コミット範囲: <base>..<head>
- ブランチ: <branch>（マージ先は <main>）

## 前提条件

- **ファイルを一切変更しないこと。** 調査用のスクリプト・一時データは
  scratchpad 配下にのみ書く。開始時と終了時に `git status --porcelain` が
  同一（通常は空）であることを実測で示す。
- 以下は「未修整である」ことが既知の前提。**それ自体を欠陥として報告しない。**
  ただし変更の意図を判断する材料としては読んでよい。
  <例: テストコードとドキュメントは旧 API のまま未修整>
  <該当なしの場合はこの節を削除する>

## ① 敵対的検証

1. **検証対象の確定**（ここを飛ばさない）
   - マージコミットが対象なら、`git log -1 --format='%H%n%P%n%B' <hash>` で
     親を辿り、**マージが取り込んだ側のベースコミットとそのメッセージ**を特定する。
     マージコミット自身のメッセージ（"Merge branch ..."）は意図を語らない。
   - `git diff --stat <base> HEAD` で**正味差分**を出す。
     変更とその revert が同一範囲に含まれ**打ち消し合っている**ことがあるので、
     個別コミットの差分の総和と正味差分を必ず突き合わせる。
     打ち消されたものは「機能影響なし」と明記し、機能指摘には数えない。
   - 確定した「ベースコミットのメッセージ ↔ 正味差分」の対応表を作る。

2. **妥当性の検証**（本手順の主目的）
   各コミットメッセージが宣言した内容に対し、実装が
   **過不足なく対応しているか**を判定する。特に次を疑う。
   - **やり残し**: 「〜を定数化」「〜を共通化」等の宣言に対し、
     同種の箇所がリポジトリ内に取り残されていないか。
     必ず `grep` で**全出現箇所を数え上げてから**判定する。
   - **やり過ぎ**: メッセージにない挙動変更・外部契約変更が混ざっていないか。
   - **無効化**: 変更が別箇所によって実効を失っていないか。
   - **理由の欠落**: revert や方針転換に根拠が記録されているか。
     記録がなければ「元の要件が解決済みか未解決か判定不能」と指摘する。

3. **影響範囲の追跡**
   変更箇所だけを見ない。変更した値・キー・不変条件が**どこで消費されるか**を
   grep で辿り、次を確認する。
   - 追加した検証（バリデーション）が、下流が実際に依存している前提を
     **本当に保証しているか**。件数だけ見て位置・順序・一意性を見ていない、等。
   - 下流に情報が伝わる経路で**キーや型が落とされていないか**
     （落ちていれば、その情報は暗黙の前提としてしか残っていない）。
   - 保証が強まった結果、**到達不能になったコード**（既定値・分岐）がないか。

4. **実測による裏づけ（必須）**
   推論だけで指摘を確定しない。scratchpad に調査スクリプトを書き、
   **実コードを呼んで**期待どおり発火する／しないことを示す。
   - 検証の発火確認は、正データを一時ディレクトリへ複製してから摂動を与える。
   - 「検知されるはず」と「検知されない」の**両方**のケースを走らせる。
   - 既存テストを実行し、実測の合否件数をそのまま引用する。
   - 数値・出力は実行結果のみを引用する。見込み値・記憶を書かない。

## ② 指摘そのものへの敵対的検証

①で出した各指摘を、**指摘する側の立場を捨てて**次の観点で潰しにかかる。
局所ではなく影響範囲全体で見ること。

- **根拠の機構的成立性**: 指摘が依拠するメカニズムは本当に成立するか。
  ツールやライブラリの挙動を根拠にする場合、その挙動を確認したか。
  確認できないなら、指摘を**確認できる範囲まで縮める**。
- **推奨対策のデグレ評価**: 対策を入れた場合に
  (a) 既存の出力・計算結果が変わらないか
  (b) 既存テストが通るか（正データが条件を満たすかを実測で確認）
  (c) 循環 import・依存増加・起動順序の破壊がないか
  デグレを生む対策案は**推奨から除外**し、除外した理由を残す。
- **互換性変更の切り分け**: 受入れ条件の厳格化は「バグ修正」ではなく
  **仕様判断**。デグレと混同せず、そう明記する。
- **既存設計との一貫性**: 指摘対象が、変更前から全経路で同じ設計なら
  「本変更による劣化ではない」と格下げする。
- **重大度の再査定**: 「破綻」なのか「情報提供」なのかを問い直す。

## ③ 再修正

②でデグレ・整合性破綻・根拠不成立を検出した指摘は、
**指摘の文言・根拠・重大度・推奨対策を書き換えて**②に戻す。
このとき**ファイルは一切変更しない**（指摘文の修正のみ）。
棄却した指摘・格下げした指摘は、消さずに反復ログとして残す。

## ④ 反復

②〜③をデグレ・整合性破綻がなくなるまで、**最大10回**繰り返す。
- なくなった場合: 収束として最終指摘を報告する。
- 10回で収束しない場合: **中止**し、収束しなかった指摘と理由を報告する。

## 報告フォーマット

1. 検証対象の確定結果（ベースコミット × メッセージ × 正味差分の対応表）
2. 実測サマリ（テスト結果・probe 出力を**実行結果のまま**引用）
3. 反復ログ（各回で棄却・格下げ・再修正した指摘とその理由）
4. 最終指摘（重大度順。各指摘に「事実／実測根拠／影響範囲／推奨対策と
   その互換性影響」を書く）
5. コミットメッセージに対する妥当性の総括（コミット単位の○×表）
6. `git status --porcelain` の実測（無変更であることの証明）

## 禁止事項

- ソース・テスト・ドキュメントを変更すること（scratchpad 配下を除く）
- ツールを呼んだつもりで結果を書くこと、実行結果を捏造すること
- 「前提条件」で未修整と宣言された対象を欠陥として報告すること
- 根拠を確認せずに機構を断定すること（確認できない部分は「未特定」と書く）
- 反復を1回で打ち切って「収束」と報告すること
```

## 付録: この手順の各規約が入った理由（実測根拠）

規約の理由が分からないと守られないので、根拠を残す。いずれも本リポジトリでの実運用時の実測。

| 規約 | 根拠 |
| --- | --- |
| マージ自身でなく**ベースコミットのメッセージ**を読む | 対象4件のマージのメッセージは全て `Merge branch ...` で、変更意図（「開始/終了地点のタイプを定数化」等）は全てベース側にしかなかった |
| **正味差分**を個別コミットの総和と突き合わせる | 4マージ中2つが「関数内 import のモジュールレベル移動」とその revert で、`function.py` の正味差分は**ゼロ**。個別差分だけ見ると存在しない変更を検証してしまう |
| 「やり残し」は**先に grep で全出現を数える** | 「タイプを定数化」に対し、定数化されたのは2箇所で、3箇所目（別ファイル）が取り残されていた。差分だけ読んでいると構造的に発見できない |
| 追加した検証が**下流の前提を保証しているか**を追う | 追加されたのは type の**件数**チェックだったが、下流は `genom[0]` / `genom[-1]` という**位置**に依存していた。件数が正しくても位置が違えばエラーにならず結果だけ誤る、という抜けを実測で再現できた |
| 情報が**落ちる経路**を探す | 中間層で `type` キーが捨てられており、開始/終了を識別する手段が配列順序しか残っていないことが、抜けの根本原因だった |
| 実測で**発火する／しない両方**を走らせる | 「0件」「2件」でエラー73が出ることだけ確認すると、抜け（位置違いが素通りする）に気づけない。両方走らせて初めて差が見える |
| ②で**根拠の機構的成立性**を疑う | 「revert により関数内 import がバンドラから見えなくなる」という指摘を出したが、主要バンドラは bytecode 走査で関数内 import も検出するため**根拠不成立**。②で自己棄却し、確認できる範囲（理由が記録されていない＝要件の状態が判定不能）まで縮めた |
| 推奨対策の**デグレ評価**を必須にする | 抜けへの対策として「型に基づく並べ替え」を検討したが、順序変更が距離計算と最適化結果を変える**デグレ**になるため推奨から除外した。対策を出しっぱなしにすると害になる |
| **互換性変更**をデグレと切り分ける | 位置検証の追加は正データ・既存テストに影響しない一方、本番入力次第で新たに実行不能になり得る。「バグ修正」ではなく仕様判断として提示する必要があった |
| **既存設計との一貫性**で格下げする | 「例外が先頭エラーのコードしか返さない」は変更前から全エラー経路で同じ設計であり、本変更による劣化ではない。格下げしないと指摘がノイズで埋まる |
| `git status --porcelain` を開始・終了で実測 | 「ファイル変更禁止」を守ったことは自己申告では示せない。無変更の実測が唯一の証拠 |
